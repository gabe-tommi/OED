OED TimescaleDB Benchmarking Summary

Formatted for project-summary handoff and easy copy/paste into Google Docs.

Overview

Purpose: improve performance of the OED database using TimescaleDB.

Key changes:

  • Implement TimescaleDB.
  • Convert the readings table to a hypertable.
  • Replace materialized views with continuous aggregates.

Goals:

  • Reduce query time.
  • Avoid full table recomputation.
  • Support time-based queries more efficiently.

Implementing TimescaleDB

SQL commands were executed using pgAdmin connected to the OED database container.

2.1 Environment Setup

  1. Start from a fresh OED install or a clean database volume.
  2. Update the Docker image in containers/database/Dockerfile:
FROM timescale/timescaledb:2.26.1-pg15
  1. Rebuild containers:
docker compose up --build

2.2 Enabling Extension

Ensure TimescaleDB is installed and available, then enable the extension in pgAdmin:

CREATE EXTENSION timescaledb;

2.3 Initialize Test Data

In the web container or local project environment, run:

npm run testData

Verify that tables were populated:

SELECT * FROM meters;
SELECT * FROM groups;
SELECT * FROM readings;

Creating a Hypertable

3.1 Create a Copy of the Readings Table

A copy of the readings table was created so the original table could remain unchanged during testing.

CREATE TABLE readings_hypertable (LIKE readings INCLUDING ALL);

3.2 Copy Existing Data

All rows from readings were inserted into the new table.

INSERT INTO readings_hypertable SELECT * FROM readings;

3.3 Verify Table Contents

The current database and row counts were checked to confirm the correct table was modified and that the copied data matched the original.

SELECT current_database();
SELECT COUNT(*) FROM readings;
SELECT COUNT(*) FROM readings_hypertable;

3.4 Convert the Table to a Hypertable

The copied table is converted into a TimescaleDB hypertable using start_timestamp as the time column.

SELECT create_hypertable(
  'readings_hypertable',
  'start_timestamp',
  migrate_data => TRUE,
  if_not_exists => TRUE
);

3.5 Verify Hypertable Creation

TimescaleDB metadata tables are queried to verify that the hypertable and its chunks were created successfully.

SELECT * FROM timescaledb_information.hypertables;
SELECT * FROM timescaledb_information.chunks;

4 Benchmarking

4.1 Script Setup

All benchmark scripts are located under src/server/test/benchmark.

  1. Start the database container:
docker compose up -d database
  1. Make sure the Timescale prototype objects exist if the benchmark depends on them. In pgAdmin, run:
containers/database/timescaledb/hypertable.sql
containers/database/timescaledb/continuous_aggregates.sql
  1. Initialize benchmark data:
npm run testData

Optional test-data generators:

npm run generateTestingData
npm run generateFifteenMinuteTestingData
npm run generateFourHourTestingData
  1. Install Node dependencies if needed:
npm install
  1. Run benchmark scripts from the project root:
npm run benchmarkBaseline
npm run benchmarkHypertable
npm run benchmarkHourlyRefresh
npm run benchmarkCaggUpdatePatterns
  1. Visualize results by opening the matching HTML file in a browser and pasting in the generated JSON.

4.2 Important Benchmark Changes

The older benchmark scripts were updated so they still run correctly against the live database.

Previously, the old scripts depended on:

  • hardcoded database credentials
  • hardcoded source and destination unit IDs
  • hardcoded date windows such as 2020 or 2024

They now:

  • derive the meter’s live reading range from the database
  • derive source_id from the selected meter
  • use the meter’s default graphic unit as destination_id unless overridden
  • generate cik_vary segments over the actual live benchmark range
  • support environment variables for database connection and meter selection
  • write output files into the benchmark directory consistently

Both older scripts also force UTC timestamp handling to avoid time-shift errors during benchmark generation.

4.3 Benchmark File Summary

benchmark.js

Run with:

npm run benchmarkBaseline

Purpose: original baseline benchmark for the expensive cik_vary overlap join.

What it tests:

  • raw readings
  • cik_vary overlap join cost
  • segment densities from one fixed segment up to dense sub-hourly variation

What changed:

  • uses live meter dates instead of fixed scenario years
  • derives source and destination context from the database
  • can be redirected with environment variables

Output: benchmark_results.json

Visualized with: benchmark_chart.html

benchmark_hypertable.js

Run with:

npm run benchmarkHypertable

Purpose: compares the same cik_vary overlap join across readings, readings_hypertable, and cagg_hourly_readings_unit.

What it tests:

  • whether the hypertable helps raw overlap-join performance
  • whether the hourly continuous aggregate reduces join cost by reducing row count

What changed:

  • uses the live meter range instead of fixed date windows
  • derives meter and unit context automatically
  • fails early with clearer messages if the hypertable or cagg is missing

Output: benchmark_hypertable_results.json

Visualized with: benchmark_chart.html

benchmark_hourly_refresh.js

Run with:

npm run benchmarkHourlyRefresh

Purpose: simulates the hourly refresh workflow and compares the old hourly materialized-view path to the new Timescale hourly continuous aggregate path.

What it tests:

  • one hour of new readings inserted
  • full refresh of hourly_readings_unit
  • incremental refresh of cagg_hourly_readings_unit
  • post-refresh query time for hourly conversion queries

What it shows:

  • continuous aggregate refresh is dramatically faster than full materialized-view refresh
  • query time is still dominated by the cik_vary overlap join at high segment counts

Output: benchmark_hourly_refresh_results.json

Visualized with: benchmark_hourly_refresh_chart.html

benchmark_cagg_update_patterns.js

Run with:

npm run benchmarkCaggUpdatePatterns

Purpose: focuses only on the Timescale update path for a single meter.

What it tests:

  • append 1 hour after latest data
  • backfill 1 hour two years before earliest data
  • insert into a future gap, then insert before it with a gap
  • append 1 day
  • append 30 days
  • append the full available history block

What it measures:

  • hypertable insert time
  • continuous aggregate refresh time
  • total update time
  • chunk growth
  • hourly aggregate rows affected

What it shows:

  • Timescale handles small and medium update patterns very quickly
  • backfill and gap patterns can create additional hypertable chunks
  • larger blocks remain fast relative to the earlier conversion-query benchmarks

Output: benchmark_cagg_update_patterns_results.json

Visualized with: benchmark_cagg_update_patterns_chart.html

4.5 Recommended Benchmark Order

  1. npm run benchmarkBaseline: establishes the original cik_vary overlap-join problem.
  2. npm run benchmarkHypertable: shows how the same query behaves on the hypertable and hourly cagg.
  3. npm run benchmarkHourlyRefresh: shows the old vs new hourly refresh workflow.
  4. npm run benchmarkCaggUpdatePatterns: shows how the new Timescale path behaves under append, backfill, gap, and bulk-update patterns.

Creating Continuous Aggregates

5.1 Hourly Continuous Aggregate

A continuous aggregate was created on top of the hypertable to pre-compute hourly averages. Unlike a regular materialized view, TimescaleDB only refreshes the buckets that have new data, so it avoids recomputing everything from scratch.

In pgAdmin, run the contents of containers/database/timescaledb/continuous_aggregates.sql.

Verify it was created:

SELECT * FROM timescaledb_information.continuous_aggregates;
SELECT * FROM cagg_hourly_readings_unit;

5.2 Daily Continuous Aggregate

A second continuous aggregate was built on top of the hourly one. TimescaleDB supports this as a hierarchical continuous aggregate, so the daily CA reads from the hourly CA instead of going back to the raw hypertable, which makes the daily rollup faster to compute.

In pgAdmin, run the contents of containers/database/timescaledb/daily_continuous_aggregate.sql.

Verify it was created:

SELECT * FROM cagg_daily_readings_unit;
SELECT * FROM timescaledb_information.jobs;

The second query confirms the automatic refresh policy was attached. The daily aggregate will now refresh itself once per day without manual intervention.
